The runner, fixtures, and memory monitor are implemented in Dart. fast_xlsx uses a local Rust build selected by hooks.user_defines.

3 fresh processes per case, each with a 16 × 10 warmup. Times exclude process startup and build hooks. Peak process RSS and dedicated temporary-directory bytes are sampled every 10 ms by a second Dart isolate. RSS is absolute process memory, not memory added by the operation.
All reads traverse every cell and pass row, cell, and checksum validation. Each library’s first export per size is independently cross-read.

## Interpretation

Across the million-cell shapes, fast_xlsx exported 1.7–2.0× faster and fully imported 4.0–5.5× faster than the fastest peer in each case. The peer with the lowest peak RSS in each case used 2.7–3.0× the process memory of fast_xlsx.

At 10k cells, fast_xlsx took 0.034 s to export and 0.020 s to import. The fastest peer took 0.054 s and 0.097 s.

For the 1M-cell tall case, fast_xlsx stream read and write sampled 4.1 and 4.1 MiB of temporary disk use. Buffered read sampled 309.6 MiB peak RSS, versus 198.5 MiB for stream read.

Recommendation: continue developing fast_xlsx for backend, single-sheet, large-file workflows. This run shows a consistent speed and memory advantage. Validate against representative user files and deployment environments before making broader claims.
